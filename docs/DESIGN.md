# datRegrade design notes

Background on why the project is shaped the way it is. The [README](../README.md)
covers usage; this file covers structure and decisions.

## Two phases, deliberately separated

`auto_regrade.py` only ever *prepares* a project: it renders scripts and writes
command files. It never invokes DGIndexNV, datMatcher, or ffmpeg.

That separation exists because the expensive part of a regrade is a judgement
call. The full default matrix is ~1000 pipelines, and no automated metric tells
you which of them actually looks like the film you are trying to match — you
have to look at frames. So the generator gets you to the point where you can
start looking, and you drive the rest yourself and re-run only what you changed.

It also means the generator is cheap and safe to run repeatedly, and it can be
tested in CI without any of the media tooling installed.

## Generated command files

Commands are recorded per step into `01_index`, `02_extract_*`,
`03_match_colors`, `04_combine_luts`, `05_capture_*`, plus a combined
`commands` file holding everything in order.

Two details make these files behave consistently:

* **They anchor themselves.** Each file starts by changing into its own
  directory, so a step behaves the same whether it is launched from the repo
  root, by double-click, or from another directory.
* **Paths are relativized.** Command lists start as absolute paths and are
  rewritten relative to the project directory at record time. A run prepared on
  one machine therefore stays valid if the repository moves, which matters when
  a regrade takes hours and the paths are long.

Tools that cannot be made relative to the project directory — a datMatcher
checkout on another drive, or `ffmpeg` found on `PATH` — are left as-is.

## The variant matrix

Source and target each get a set of *variants*, and the interesting result is
usually the cross product rather than either side alone.

* Source variants: `plain`, each configured LUT, each tonemapper.
* Target variants: `plain`, `hdr`, each configured LUT, each tonemapper.

`plain` ↔ `hdr` is a special pairing (HDR source with no conversion, against an
HDR target) and is skipped against the other variants. Where a source variant
is itself a LUT, the match LUT is composed with it so that the pipeline remains
a single LUT for the capture step — that composition is what
`datregrade/cube.py` exists for.

## LUT composition

Composing `a` then `b` means `b(a(rgb))`. Because `a`'s output rarely lands
exactly on `b`'s grid points, this requires interpolation, and the choice of
method is visible in the result.

`datregrade/cube.py` implements:

* **Tetrahedral** interpolation, the default. It is what the generated AviSynth
  scripts request via `DGCube(..., interp="tetrahedral")`, so composing here and
  applying there agree.
* **Nearest neighbour**, kept because the original helper script offered it.

Three conventions are load-bearing and are pinned by the test suite, because a
reimplementation can be self-consistent and still disagree with the original
tool on any of them:

1. **File ordering.** `.cube` entries run red axis fastest, then green, then
   blue, so a naive reshape gives `[b, g, r]`. The module transposes
   immediately and uses `[r, g, b]` everywhere else.
2. **Interpolation.** Composition always samples tetrahedrally. The `--method`
   flag only reaches the resampling helper, matching the original script, where
   applying nearest-neighbour to a composed grid introduced visible
   quantization error.
3. **Tie-breaking.** Nearest-neighbour resampling rounds exact `.5` fractions
   *down*. `numpy.rint` rounds halves to even, which differs on exactly-tied
   inputs (resampling 3 → 5 hits them, and so does the real 65-point LUT).

Rather than only assert internal consistency, `tests/test_cube.py` compares
against a reference `.cube` generated by the original LUTify script, and the
implementation was additionally checked cell-by-cell against that script across
sizes, mixer values, and both interpolation methods.

## Why datMatcher is not vendored

datMatcher's `extract_colors` links FFmpeg, so its binaries are large and are
rebuilt independently of this project. Earlier revisions of datRegrade kept
several copies of those binaries under `UTILS/datMatcher/` (including `v1`,
`v2`, `v3` snapshots), which is why that directory grew past 500 MB.

Copying them here would mean shipping stale binaries and a very heavy
repository. Instead the executables are resolved at run time from
`--datmatcher-dir`, `$DATMATCHER_DIR`, or a `utils/datMatcher/` directory next
to the script, and the resolved path is what gets written into the generated
commands.
